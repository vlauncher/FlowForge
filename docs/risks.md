# Risk Register & Mitigation Strategy

This document establishes the project risk register for FlowForge across architectural, operational, security, and AI execution dimensions. Each risk is evaluated with likelihood (Low / Medium / High), impact (Low / Medium / High), mitigation controls, and the owning project phase.

| ID | Category | Risk Description | Likelihood | Impact | Mitigation Strategy | Owner Phase |
|---|---|---|---|---|---|---|
| R-01 | Reliability | **Worker Crash Mid-Step:** Worker process is terminated (OOM, SIGKILL, network drop) after step executes side effect but before committing database transaction. | High | High | Dual-write prevention using Transactional Outbox pattern with lease-based heartbeats (`step_attempts.heartbeat_at`). External calls record an idempotency record before execution; recovery sweeper detects expired leases and reconciles state without duplicating side effects. | Phase 4, Phase 7 |
| R-02 | Security | **SSRF / Internal Network Probing:** Malicious or compromised workflow definitions configure outbound HTTP tool steps targeting AWS/GCP metadata endpoints (`169.254.169.254`) or internal loopback/private RFC 1918 CIDRs. | High | High | Strict security CIDR blocklist (`spec/00-global.md` §7), DNS-rebinding verification (resolving IPs before dialing), and pre-approved org-level domain allowlists. Enforced at the adapter layer before TCP socket creation. | Phase 3 |
| R-03 | Security | **Tenant Cross-Contamination / Data Leakage:** A bug in API query filters exposes organization B's workflow run inputs, outputs, or integration secrets to a user in organization A. | Medium | High | Multi-tenant isolation enforced at the database repository query layer (`WHERE organization_id = :org_id` on every query), integration testing with multi-org fixture matrix, and strict tenant context propagation. | Phase 2, Phase 3 |
| R-04 | Cost & Limits | **Free LLM Quota Exhaustion / Unexpected Billing:** Free OpenRouter tier quotas (20 RPM, 50 RPD) are exhausted, or an unauthorized non-free model is requested, causing runtime failures or billing charges. | High | Medium | Hardcoded model allowlist rejecting any model lacking `:free` suffix; local in-memory token/request rate limiter (20 RPM / 50 RPD window) that pauses/queues steps instead of dropping; deterministic `FakeLLM` adapter used in automated tests. | Phase 6 |
| R-05 | AI Reliability | **Hallucinated or Malformed Tool Arguments / Structured Output:** Generative model returns non-conforming JSON, invalid types, or hallucinated parameter fields in an LLM step. | High | Medium | Strict Draft 2020-12 JSON Schema validation on all LLM responses; retry loop with bounded attempts (max 3) injecting schema violation feedback into model prompt; terminal step failure with RFC 9457 details on exhaustion. | Phase 6 |
| R-06 | Security | **Credential & Secret Leakage in Logs / Traces:** Third-party API keys, bearer tokens, or user passwords appear in structlog stdout logs, Sentry events, or OpenTelemetry trace spans. | Medium | High | Centralized `redaction.py` processor with recursive regex matching on sensitive keys (`password`, `token`, `secret`, `authorization`, `api_key`, `cookie`), depth-bounded, integrated into structlog processor pipeline and error handlers. | Phase 1, Phase 3 |
| R-07 | Operational | **Outbox / Broker Poison Pill Loop:** A corrupt or unprocessable message in RabbitMQ is repeatedly redelivered to workers, causing worker thrashing and queue saturation. | Medium | High | Maximum delivery count (Dead Letter Exchange / DLX routing after 3 failed attempts); poison messages routed to `flowforge.dlq` with diagnostic context; Prometheus queue lag alerts. | Phase 4, Phase 8 |
| R-08 | Performance | **Asyncio Event-Loop Starvation:** Synchronous, blocking I/O calls (e.g. `requests.get`, `time.sleep`, heavy CPU serialization) invoked inside async FastAPI route handlers or async worker loops block all concurrent requests. | Medium | High | Strict architecture rule banning sync blocking I/O in async code paths; offloading CPU/sync tasks to `asyncio.to_thread` or Celery workers; event-loop monitoring and test assertions. | Phase 1, Phase 5 |
| R-09 | Operational | **Stale or Lost Human Approval Signals:** An approval request remains in `WAITING_APPROVAL` indefinitely when the designated reviewer is unavailable or leaves the organization. | Medium | Medium | Configurable `timeout_seconds` on approval steps with explicit `timeout_action` (`fail` or `skip_step`); automatic notification dispatch; expiration sweeps transitioning timed-out runs to `TIMED_OUT`. | Phase 5 |
| R-10 | Reliability | **Database Connection Pool Exhaustion:** Sudden spike in concurrent worker tasks or long-running database transactions starves the SQLAlchemy connection pool. | Medium | High | Explicit pool sizing (`pool_size=20`, `max_overflow=10`, `pool_timeout=10`), short-lived database transactions, separating read queries from worker long-polling, and health probes with pool saturation metrics. | Phase 2, Phase 8 |
| R-11 | Data Integrity | **Race Conditions on Concurrent Step Execution:** Two upstream dependencies complete simultaneously in a DAG workflow, triggering concurrent worker attempts to advance the workflow run state machine. | Medium | High | Optimistic concurrency control via `runs.version` column with `SELECT ... FOR UPDATE` or conditional `UPDATE runs SET status = ... WHERE id = ... AND version = :version`; state transition table enforces valid transitions. | Phase 4 |
| R-12 | Security | **Replay Attacks on Inbound Webhooks:** Malicious actor captures valid third-party webhook payload and resends it repeatedly to trigger duplicate downstream workflow executions. | High | High | Inbound webhook verification requiring HMAC-SHA256 signature check, 5-minute maximum timestamp skew window, and webhook delivery deduplication table (`idempotency_keys` / `webhook_deliveries`). | Phase 3, Phase 7 |
| R-13 | Security | **Email Enumeration & Timing Attacks:** Malicious actors probe `/v1/auth/login` with target emails to discover registered accounts by measuring response timing differences between existing and non-existent accounts. | High | Medium | Constant-time password verification utilizing a pre-computed Argon2id dummy hash (`DUMMY_PASSWORD_HASH`) when an email is not found, equalizing execution timing; generic "Invalid email or password" error messages. | Phase 2 |
| R-14 | Security | **Shared-Schema Multi-Tenant Query Leaks:** Developer oversight in a shared database architecture could omit tenant filters, leaking workflows, credentials, or runs across organizations. | Medium | High | Defense-in-depth: (1) Mandatory `*, org_id: UUID` keyword-only parameter on all repository methods, (2) Automated static AST analysis in CI (`scripts/check_tenant_params.py`), (3) HTTP 404 (Not Found) returned for non-member organizations to prevent existence probing, (4) Composite B-tree indexes prefixed with `org_id`. | Phase 2 |
